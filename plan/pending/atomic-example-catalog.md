# Atomic example catalog: hand-authored documents, auto-derived projections

## The idea (one paragraph)

Build a **catalog of atomic examples** where the *documents are hand-authored* (one
meaningful instance per atomic document type, living in the domain's
`example/document/*.jl` file) and the *projections are discovered* (for each document,
find its most trivial single-step projection, then a projection to `:text`, then one to
`:graphics` if reachable). Organise the catalog as a small **hierarchy** — domain →
document → projection variant — so any slice is a one-line filter. This replaces
`AtomicFixtureTest` and lets us delete the manual registry examples that exist only to
carry one atomic document, while running the *existing* example testers
(`test_printer` / `test_reader` / `test_repl` / `test_position_navigation`) over the
whole catalog.

## Relationship to `discovered-example-catalog.md`

This **supersedes Phases 1–3** of
[`plan/pending/discovered-example-catalog.md`](discovered-example-catalog.md) and keeps
its **landed Phase 0** as the foundation (the projection graph — `BRIDGES`, `_step`,
`path_sequences`, `paths`, `projection_to`, and `Example.terminal` — already on `main` in
[`package/projectured/example/Catalog.jl`](../../package/projectured/example/Catalog.jl)
and [`CatalogTest.jl`](../../package/projectured/test/projection/CatalogTest.jl)).

**The one pivot from the old plan:** documents come from a *hand-authored registry*, not
from `minimal()`. This is a net simplification and a fidelity win:

- The entire risky `minimal()` / `@document`-reflection / `document_field_types` /
  `CellVector{T}`-annotation track (old Phases 0-doc-side + 1, the one that was *blocked*
  by the cell-kind work) is **deleted, not fixed**. No `@document` change is needed.
- Hand-authored documents carry *meaningful* content (`JsonString("Hello, world")`, not
  `JsonString("")`), so the pipelines are exercised the way a real editor would — the
  `minimal()` empty-content under-exercise concern goes away.

The projection *automation* is exactly what the old plan built and is reused verbatim.

## Design

### 1. Atomic documents — hand-authored, registered with a hierarchy

An **atomic document** is a small, leaf-ish document whose value stands alone (a JSON
scalar, a primitive, a math variable, a markdown text run, …). We do **not** try to
auto-generate them; a human writes each one meaningfully in the domain's example file.
They are tagged only enough to filter.

```julia
# kernel-example/Harness.jl (next to `Example`)
struct AtomicDocument
    name::String        # "json_string"        (level 2 of the hierarchy)
    domain::Symbol      # :json                (level 1 of the hierarchy)
    make_document       # thunk -> a fresh, unaliased instance
end
```

Documents live in the existing per-package example files and are collected into one
registry the way `domain_examples` / visual example slices already are (each package
contributes its slice; `ProjecturedExample` concatenates into `atomic_documents`).
Reuse the makers that already exist — `make_json_null_document_example`,
`make_json_string_document_example`, `make_primitive_string_document_example`, … — and
add the missing atoms (`make_json_bool_…`, `make_json_number_…`, `make_math_variable_…`,
`make_markdown_text_…`, `make_primitive_number_…`, `make_primitive_bool_…`, and the
`*Insertion` / other leaf docs surfaced by the method-table scan below).

The authoritative "what atoms exist" list is **runtime**, not a source grep: the
single-step leaf projections are macro-generated by `@projection_template`, so they show
up in `methods(print_document)` (what Phase 0 already reflects over) but not in source.
Phase A begins by dumping that table to enumerate every leaf document type that has a
trivial projection, then hand-authors one meaningful instance for each.

### 2. Projections — discovered per document

For each `AtomicDocument`, `catalog()` builds **up to three** `Example`s:

| variant | terminal | how it's found | runnable? |
|---|---|---|---|
| atomic single-step | `:syntax` (usually) | `atomic_projection_for(typeof(doc))` — the trivial zero-arg leaf projection from the `print_document` method table | no (can't be shown) |
| → text | `:text` | `projection_to(doc, is_text)` over the projection graph | yes → console |
| → graphics | `:graphics` | `projection_to(doc, is_graphics)` over the projection graph | yes → screen / web |

`atomic_projection_for(::Type{D})` is the inverse method-table lookup already prototyped
inside `discover_atomic_pairs`: scan 5-param `print_document` methods, keep the one whose
doc parameter is `D`'s umbrella and whose projection parameter is a zero-arg-constructible
`Projection` producing a `SyntaxDocument`. "Most trivial" = the leaf `*ToSyntaxLeaf`
stage; if more than one qualifies (rare), pick deterministically by name and allow an
explicit override map. `projection_to` / `path_sequences` are used **unchanged** from
Phase 0, but seeded with the *hand-authored* instance instead of `minimal(D)`.

A variant that isn't reachable (e.g. an atom with no path to `:graphics`) is simply
skipped — "and another to graphics **if possible**".

### 3. Hierarchy & filtering — the name *is* the path

Every catalog entry is keyed by three axes, and the `Example.name` encodes them as a
**hierarchical `/`-path** `domain/document/variant`, so filtering is just prefix matching:

```
catalog
 └─ domain          json, xml, primitive, math, markdown, formula, sql, …   (AtomicDocument.domain)
     └─ document     null, bool, number, string, …                          (AtomicDocument.name stem)
         └─ variant  syntax │ text │ graphics                               (Example.terminal)

names:  json/string/syntax     json/string/text     json/string/graphics
        json/null/syntax       json/null/text       json/null/graphics
        primitive/number/text  primitive/number/graphics   …
```

The third component is the `Example.terminal` — the trivial single-step entry is `syntax`
(its usual terminal), the reachability entries are `text` / `graphics` — so name-prefix
filtering and field filtering describe the *same* hierarchy:

```julia
filter(ex -> startswith(ex.name, "json/"),        catalog())   # a whole domain
filter(ex -> startswith(ex.name, "json/string/"), catalog())   # one document's variants
filter(ex -> endswith(ex.name, "/graphics"),      catalog())   # everything runnable on screen
```

The structured filters remain as a convenience over the same axes (implemented against the
`atomic_documents` registry, no name parsing):

```julia
catalog(; domain=nothing, document=nothing, terminal=nothing, only_runnable=false)
```

No wrapper struct — each entry stays a plain `Example` that plugs straight into
`test_printer(ex)` / `run_example(ex)`. Names must be unique; the rare case where a
trivial single-step projection shares a terminal with a reachability variant gets a
disambiguating suffix (`#2`), as `reachability_examples` already does for multiple paths.

### 4. Marking generated vs. manual

Add one field to `Example` to satisfy "mark examples being derived automatically or
created manually":

```julia
struct Example
    …existing fields…
    terminal            # existing
    origin              # NEW: :manual (hand-authored registry) | :generated (catalog)
end
```

`origin=:manual` by default (every existing call site unaffected); `catalog()` stamps
`:generated`. The *document* is hand-authored, but the document+auto-projection *pair* is
generated — so the pair is `:generated`, and the curated application examples (`json`,
`workbench`, …) stay `:manual`. Screenshot gallery / tour filter to `:manual`.

## Replace `AtomicFixtureTest` & prune the registry

- **Delete** [`package/domain/test/projection/AtomicFixtureTest.jl`](../../package/domain/test/projection/AtomicFixtureTest.jl)
  and its wiring in `ProjecturedDomainTest.jl` (`include`, `test_atomic_fixtures()` call,
  the `AtomicFixture` / `test_atomic_render` / `test_atomic_fixtures` exports; likewise the
  re-exports in `ProjecturedTest.jl`). The generic testers over the catalog subsume the
  no-throw / structural coverage.
  - *Consciously dropped* (the "I don't need the fixture part" call): the exact-render
    goldens (`render(out)=="null"`), the `mutate` reactivity probe, and node-stage-in-
    isolation via mocked children. Node stages stay covered **in composition** by the
    `→ text` / `→ graphics` variants (they run the real `RecursiveProjection(JsonToSyntax())`,
    which includes `JsonArrayToSyntaxNode`); cell reactivity stays covered by `test_cell()`.
    → If any of these is later missed, re-add it as an optional oracle on the catalog entry,
    not as a parallel fixture file.
- **Wire `test_catalog()` into the aggregators** (it already exists and is terminal-aware;
  it is currently defined + exported but never called). Add it to the domain / umbrella
  test run so the catalog actually executes in the suite.
- **Prune atomic-only registry entries.** Remove `json_null_example`, `json_string_example`,
  `primitive_string_example` from the `examples` list and delete their `const *_example`
  definitions — the catalog now produces the equivalent (and better: the same hand-authored
  document under the auto-derived atomic / text / graphics projections). **Keep the document
  maker functions** (`make_json_null_document_example`, …); they become the
  `AtomicDocument.make_document` thunks. This is the earlier fidelity concern resolved: we
  reuse the *meaningful* hand-authored document, we just stop registering a bespoke Example
  for it.
  - The old flat handles (`run_example("json_null")`) are **not** aliased. The catalog
    exposes each atom under its hierarchical name instead — `run_example("json/null/graphics")`,
    and `run_console_example("json/null/text")` — which doubles as the filter path. No
    back-compat alias layer.

## Decisions (settled)

1. **Where the catalog runs.** Keep `examples` as the curated hand-authored registry
   (gallery / screenshots / `run_example`-by-name unchanged) and drive the catalog through
   the already-written `test_catalog()`, wired into the aggregator. Lowest churn, and
   `test_catalog`'s terminal-aware routing is strictly better than the name-based skip-lists
   the sweeps carry. (Rejected alternative: appending `catalog()` into the single global
   `examples` — balloons the gallery/screenshots and confuses the name skip-lists.)
2. **AtomicFixture goldens — dropped** (confirmed by the user). `AtomicFixtureTest.jl` and
   its exact-render goldens + `mutate` reactivity probe + node-in-isolation fixture are
   deleted outright; the generic testers over the catalog take their place. Re-add as an
   optional oracle only if a concrete gap shows up.

## Implementation results (2026-07-15)

**Scope landed:** **27 atoms → 81 catalog entries** (Phase A + D). json (null/bool/number/string),
yaml (null/bool/number/string), primitive (string/number/bool), xml/text, markdown
(text/code/thematic_break), math/variable, julia (9 leaves), book (paragraph/picture) — each × the
three `domain/name/{syntax,text,graphics}` variants. Bridges: json/xml/yaml/julia/markdown/math/book
→ syntax, syntax→text, text→graphics. `test_catalog()` (printer/reader/repl over all 81 +
position-navigation over the 27 `:graphics` entries) → **43037 assertions pass, 0 fail/error/broken**.

**Design facts confirmed during implementation:**
- The reachability graph (`BRIDGES`) only reaches text/graphics for domains with a whole-tree
  bridge (json/xml/yaml/julia/markdown). **Primitives** reach text via a *direct single-step*
  (`Primitive*ToText*`), which `_text_sequence` tries before the bridge BFS; graphics is then the
  text sequence chained with the `_TEXT_TO_GRAPHICS` tail (graphics only ever arrives via text).
- Building the catalog is cheap — projection *objects* are constructed, not run (the slow
  `TextToGraphics` fires only when a test/example actually prints a `:graphics` entry).

## Bugs surfaced by the catalog — and fixed

The catalog did its job and surfaced two **pre-existing** problems that no prior example
exercised. Both are now fixed (not skipped):

1. **`JsonBool`/`YamlBool` bare-root round-trip crash — `TypeError(:if, …, Bool, nothing)`.**
   A REPL edit on a bare-root bool transiently clears the type-erased `value` cell to a
   non-`Bool`; the reprint thunk `() -> doc.value ? "true" : "false"` then hit `if nothing`.
   `JsonBool.value::Bool` (unlike `JsonNumber.value::Union{Real,Nothing}`) had no guard.
   **Fix:** render the thunk through `hinted_text(…, () -> !(doc.value isa Bool), …)` — the
   same lazy guard `JsonNumberToSyntaxLeaf` uses — so the `? :` is never evaluated on a
   non-`Bool` (JsonToSyntax.jl / YamlToSyntax.jl). Normal `true`/`false` rendering is unchanged.
2. **Position-navigation needed the `:graphics` terminal, not `:text`.** `Ctrl+Home` (and the
   arrow steps) move the caret by *visual* geometry, which only `TextToGraphics` computes — the
   `:home` seed reader lives there. The catalog routed `test_position_navigation` to `:text`
   entries (which stop before `TextToGraphics`), so the seed returned `nothing` (0 states — a
   fail-safe, not a runaway). The manual `text`/`json` examples navigate precisely because their
   projections run through `TextToGraphics`. **Fix:** `_required_terminal(test_position_navigation)
   = :graphics` in `CatalogTest.jl`; it runs on the 13 `:graphics` entries and is back in the
   default testers. (No flat-offset-reader work was needed — the diagnosis was a wrong-terminal
   routing, not a missing reader.)

**Pruning coverage note:** removing `json_string` dropped two of its bespoke assertions — a
`test_json_content_clicks_clean` case and a known-`@broken` typein marker ("no operation at the
last caret"). The full `json` example still covers string editing; the catalog covers
`json/string` for printer/reader/repl. Net effect on counts: one fewer `Broken` (the removed
typein marker) — expected, not a regression.

## Risks / decisions

- **`_single_step` ambiguity.** Two zero-arg leaf projections for one doc type with the same
  output terminal is rare; resolved deterministically (lexicographically-first projection name).
  An explicit override map is the escape hatch if a wrong one is ever picked.
- **Not every atom reaches `:graphics`.** Expected — emit only the reachable variants
  ("if possible"); an atom with only a `:syntax` variant still feeds printer/reader/repl.
- **`@document` is untouched** (the old plan's riskiest surface). Dropping `minimal()`
  removes that risk entirely — a key advantage of this direction.
- **Heavy Julia runs are the user's to run externally.** Verify with `test_cell()`,
  targeted domain/printer tests, and narrow `test_catalog(; domain=…)` slices; do not
  `test_all()` on Opus.
- **Fidelity vs. the real pipeline.** An atom tested in isolation can pass while failing in
  full composition; the curated application examples (`json`, `workbench`, …) remain the
  integration gate. The catalog is the fast, broad, additive signal.
