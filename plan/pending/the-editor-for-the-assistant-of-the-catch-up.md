# The editor for the assistant of the catch-up

**Status:** a plan with steps since 2026-11-19 (section 4). Each step starts only after the owner
approves it. The lists were written 2026-11-18 by the assistant of the
campaign window of omnet-julia, which follows the INET baseline catch-up in the IDE
(`bin/omnet_ide --assistant=acp ~/workspace/ghci-baseline-catch-up`), at the request of the
owner: "collect the issues which should be fixed in the next version of the editor to make your
life easier". The findings come from the live check of
[the-ide-follows-the-baseline-catch-up.md](../../../omnet-julia/plan/pending/the-ide-follows-the-baseline-catch-up.md)
(omnet-julia, step 11), which holds the details of each case. The assistant adds a row when it
meets a new one.

## 2. Names that the assistant could not write

The system text of the window lists the names that the code can write. These were missing or
different, and each cost a failed call and a search:

| # | Name | What happened | Fix idea |
| --- | --- | --- | --- |
| N1 | `Explorer` | Not among the names; `ExplorerSection` and `Dashboard` are. The assistant took it from `ProjecturedPlatform.ExplorerModule`. | List `Explorer` with the explorer verbs. |
| N2 | `Dates`, `ProjecturedKernel`, `ProjecturedPlatform` | Not imported in the scratch module; a `Dates.unix2datetime` or a type name with its module fails. | Import `Dates` in the scratch module; say in the system text how to reach a module. |
| N3 | `get_file_disk_state`, `is_folder_watched`, `find_file_change_store` | Not in the names; `is_folder_watched(store, folder)` differs from its real signature `is_folder_watched(path; store, receiver)`. | The state of a file against the disk as a verb for the assistant: the counts of the watch, the band, the stamp. |
| N4 | `describe_undo_history(buffer)` | No method for an `UndoBuffer`; only the editor-wide form exists. | A form that takes a document or a file. |
| N5 | `get_session_open_file_list()` | Answers a plain `OpenFileList`, which cannot be iterated: "Pass a part, a document with its place". | Answer a part, or document the field `files`. |
| N6 | `has_unsaved_edits(file)` | Answers `nothing` for a file; `true` or `false` only for its history (`file.content`). | A method for the file. |

| W8 | Remote Control of the agent of the chat pane (the owner, 2026-11-18: "can I enable remote control of the agent here?"). `claude` 2.1.309 offers `claude --remote-control` for an interactive session and `claude remote-control --session-id <id>` to reattach; the IDE starts the agent as `claude -p` with a stream of JSON, which has no such option, and a second session on the same id has no tools of the editor and is a second actor on the job copy. | The owner could follow the walk and answer the approval of a step from claude.ai/code or the phone. The start of the agent by the IDE and the ACP adapter would need the option. Found on 2026-11-19: `claude -p` takes the control request `{"subtype": "remote_control", "enabled": true}` on its stream of JSON, as the Agent SDK sends it, and the answer holds `session_url` and `connect_url`. The same process, with the tools of the editor, takes the turns from the phone, so there is no second actor. The work in ClaudeCodeACP.jl: (1) a session option "Remote Control: off / on", which the bar of the Assistant pane shows next to Model, Effort and Mode; (2) send the request and show the link in the chat; (3) turn it on again after each restart of `claude` (`reattach_session_id`); (4) show a turn that starts from the phone. A question of permission still goes to the editor. The help of `claude` does not list the request, so the first part is a test, which opens a real Remote Control session on the account of the owner. Tested on 2026-11-19 with `claude` 2.1.309 and no prompt: the request with `enabled: true` answers `success` in about 1 s with `session_url`, `connect_url`, `bridge_epoch` and `bridge_session_id`, and the process writes `system/bridge_state` with `ready`, then `connected`; `enabled: false` answers `success`. With a message from the Claude app for Android ("Hi there"), the process writes `command_lifecycle` `queued` and `started` (its `command_uuid` is the uuid of the message), `system/init`, then the message as a `user` event with its text as a string, `"isReplay": true` and `"origin": {"kind": "human"}`, then the answer and a `result`, and `command_lifecycle` `completed`. So the echo of a message from the phone has the same `isReplay` as the echo of a message of the editor. The design, decided by the owner on 2026-11-19 ("yes, it's fine"): (1) a fourth option "Remote Control: Off / On" in the bar, which restarts nothing, sends the request at once, and starts `claude` when it does not run; (2) the link as one line in the chat, with no change in the editor and no new kind of message; (3) after each new start of `claude`, the request again with `reattach_session_id`, so the link stays; (4) a message from the phone shows in the chat as the message of the person, and does not count as a message of a prompt of the editor. Limits: a question of permission goes to the editor; a `claude` that ended by itself stays off until the next prompt of the editor. |

the owner approves it. A fix reaches the IDE of the owner only after a new build of `omnet_ide`
and a restart, which stops the walk for a moment; so one build follows steps 1 and 2.
